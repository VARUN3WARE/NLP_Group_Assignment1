  PART 4 - "Speed Demon" benchmark (Method A vs Method B)
==============================================================================

Model: LanguageModel(types=40,542, tokens=901,816, bigrams=385,197, k=0.01)

Batch: exactly 1,000 misspelled (non-word) tokens, mean length 5.83
  sample: rway, byble, eveni, thze, simpliy, soldi, comr, lengdh, tpold, squbs

Preprocessing (paid once, at start-up)
  Method A :      0.0 ms   (just holds a reference to the vocabulary)
  Method B :    141.8 ms   (313,857 keys, 348,252 postings)

method                                       total     per word    words/sec   candidates
-----------------------------------------------------------------------------------------
Method A  (edit-distance-1 generation)     0.0504s     0.0504ms       19,860        3,166
Method B  (symmetric delete + verify)      0.0037s     0.0037ms      269,474        3,166
Method B  (symmetric delete, raw)          0.0016s     0.0016ms      619,662        6,461

Output equivalence: Method A and Method B (verified) disagree on 0 of 1,000 words.

Why the difference - strings constructed for the whole batch
  Method A :    352,312  = n + (n-1) + n|A| + (n+1)|A|, with |A| = 27
  Method B :      6,827  = n + 1
  ratio    :       51.6x more strings built by Method A

Speed-up: Method B is 13.6x faster than Method A (31.2x without the edit-distance verification step).
Method B's 142 ms index build pays for itself after about 3,040 lookups.

CONCLUSION
----------
Method B is 13.6x faster per word (0.0037 ms vs 0.0504 ms), and the
reason is entirely structural rather than a constant-factor implementation win.

Method A's cost is tied to the size of the alphabet. For a word of length n it
must materialise n deletions, n-1 transpositions, n*|A| replacements and
(n+1)*|A| insertions - roughly 2n|A| strings, with |A| = 27 here. Every
one of those strings is allocated, hashed, and probed against the vocabulary
set. Across this batch that is 52x more string construction than Method B
does, and string building plus hashing is exactly where the time goes.

Method B moves that work off the query path and into a one-off preprocessing
step. Because "one deletion on each side" is enough to cover all four edit
operations, the index only has to store each vocabulary word plus its n
deletions - 313,857 keys and 348,252 postings here, built in 142 ms. At
query time the alphabet has vanished from the complexity: only the n+1 probe
strings (the word plus its own deletions) are built, so lookup is O(n) hash
probes instead of O(n|A|). That is the whole trick - the alphabet factor is
paid once at build time instead of on every single lookup.

The verification step costs something: raw bucket lookup is 31.2x faster than
Method A, and adding the exact edit-distance-1 check brings that down to
13.6x. It is worth paying, because SymSpell buckets can collide at edit
distance 2 ("abc" and "axb" both delete to "ab"), so without verification
Method B returns a superset rather than the true edit-distance-1 set. With
verification the two methods return byte-identical candidate sets.

The trade is memory and start-up time for query latency. The index costs
142 ms to build and pays for itself after roughly 3,040 lookups - so for a
one-shot correction Method A is fine, and for anything interactive or batched
Method B is the only sensible choice.
